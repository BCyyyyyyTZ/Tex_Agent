## 一、背景与目标

- **问题**：在 WSL 等环境跑 `python -m ui.web.server` 时，用系统默认方式「打开浏览器」会走 `xdg-open`，若 Linux 侧未装浏览器会刷屏报错，且用户更希望用 **Windows 默认浏览器** 或 **VS Code Simple Browser**。
- **目标**：统一「打开 URL」逻辑；在网页上**可视化对话分支**、**自己拼工作流**、**上传 PDF 到本地目录**；保存工作流时做**图论校验**，避免无效配置。

## 二、启动后自动打开浏览器（WSL / 本机）

### 2.1 模块

| 文件 | 作用 |
|------|------|
| `ui/web/browser_open.py` | `open_http_url(url)`：WSL 下优先 `wslview` / PowerShell `Start-Process` / `cmd start`，避免纯走 `xdg-open`；否则回退 `webbrowser.open`。 |
| `ui/web/ide_launch.py` | 服务启动约 1s 后调度打开聊天页；默认 **先** 用 `open_http_url`（系统/Windows 浏览器）；可选 `TEX_AGENT_ALSO_OPEN_SIMPLE_BROWSER=1` 再试 Simple Browser；与 `TEX_AGENT_OPEN_IDE_CLI` 等旧逻辑兼容。 |
| `scripts/start_texagent_web.py` | 子进程起 `python -m ui.web.server`，延迟后调用 `default_open_chat_after_start()`，与 `ide_launch` 策略一致。 |

### 2.2 环境变量（摘录）

- `TEX_AGENT_NO_OPEN_BROWSER=1`：不自动打开**外部**浏览器。
- `TEX_AGENT_ALSO_OPEN_SIMPLE_BROWSER=1`：在系统浏览器之后再尝试当前 IDE 的 Simple Browser。
- `TEX_AGENT_NO_OPEN_SIMPLE_BROWSER=1`：不尝试 Simple Browser。
- `TEX_AGENT_NO_REMOTE_IDE_FOR_SIMPLE=1`：不向 PATH 里带 `remote-cli` 的 `code`/`cursor` 回落（WSL/Remote 场景默认允许回落以打开宿主编辑器）。
- 详见 `ide_launch.py` 模块顶部文档字符串。

### 2.3 行为说明

- 默认以**系统默认浏览器**为主（用户反馈后从「先 Simple 再浏览器」改回当前策略）。
- VS Code / Cursor 内仍可用扩展快捷键 **Ctrl+Alt+T**（Mac：**Cmd+Alt+T**）打开 Simple Browser，与 Python 侧自动打开是两条路径。

## 三、对话分支（Branch）可视化与 REST API

### 3.1 与现有逻辑的关系

- 分支语义来自 `memory/branch_memory.py`（`parent`、`create_branch`、`switch_branch`、`get_branch_info` 等）。
- CLI 侧早已有 `TeXAgentCLI.create_branch` / `switch_branch`；本次为 Web 增加**只读树数据**与**HTTP 操作**，并在 `create_branch` / `switch_branch` 上补充**返回值**与 `get_branch_tree_for_api()`。

### 3.2 后端（`core/agent_cli.py`）

- `create_branch(name, from_branch) -> bool`：各 `BranchMemory` 均需创建成功才为 `True`；`from_branch` 会做 `strip`。
- `switch_branch(name) -> bool`：`use_branch` 时在 `shared.list_branches()` 中找不到则返回 `False`。
- `get_branch_tree_for_api() -> dict`：返回 `current` 与 `nodes[]`，每项含 `id`、`parent`、`size`（记忆条数）、`messages`（该分支 `ContextManager` 对话条数）。
- `_which_ide_for_simple_browser`：在需要向 IDE 发 Simple Browser 命令时，可在无「本机」`code` 时回落到 PATH 中带 `remote-cli` 的包装（WSL 场景）。

### 3.3 FastAPI（`ui/web/server.py`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/branches` | 当前分支 + 全部分支节点信息 |
| POST | `/api/branches` | body：`name`、`from_branch`，创建子分支 |
| POST | `/api/branches/switch` | body：`name`，切换当前对话分支 |

### 3.4 前端

- `static/branch_graph.js`：拉取 `/api/branches`，按深度分层画 **SVG**（父子连线）；当前分支高亮；点击节点调用 `switch`；表单「新分支名 + 从某父节点」调用 `create`。
- `index.html` / `styles.css`：分支区块文案与样式。

### 3.5 与聊天的关系

- 切换分支后，后续 `POST /api/chat` 使用服务端 `TeXAgentCLI` 的**当前分支**（无需在每条消息里带 branch 字段，除非以后扩展多标签并发）。

## 四、左侧自定义工作流编排

### 4.1 动机

- 注册表工作流在 `config/workflow_registry.json` + 各 `config/workflow_*.json`；希望在网页里**编辑节点与边**并立即用于 `task`，而不必手写 JSON 文件。

### 4.2 构图入口（`workflow/graph_builder.py`）

- `build_app_from_workflow(..., config_dict: Optional[Dict] = None)`  
  - 若传入 `config_dict`（含 `nodes`、`edges`），则用 `YAMLWorkflowParser` 在内存中解析，**不**走 `load_workflow_graph_config(workflow_name)`。
  - 与原有「按名称读文件」路径共用 `build_dynamic_graph`。

### 4.3 Web 进程内状态（`ui/web/server.py`）

- `TeXAgentWebUI` 子类增加 `web_workflow: Dict`，默认深拷贝 `DEFAULT_WEB_WORKFLOW`（与默认链类似的简化 `design → deliver`）。
- 重写 `_build_app_for_workflow`：当 `workflow_name == "__web__"` 时，用 `config_dict=self.web_workflow` 调用 `build_app_from_workflow`；否则 `super()` 走注册表。

### 4.4 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/workflow/draft` | 返回当前内存草稿 `nodes` / `edges` |
| PUT | `/api/workflow/draft` | 保存草稿；先 `_validate_workflow_dict` 再写入 `web_workflow` |
| GET | `/api/workflow/registry` | 注册表中可用工作流名称列表（填顶栏下拉） |

### 4.5 聊天如何选中「左侧图」

- 请求体 `ChatRequest.workflow`：传 `"__web__"` 表示使用左侧保存的图；传 `null` 或选顶栏 `default` 等与 CLI 一致（`run_task` 里 `workflow_name or DEFAULT`）。

### 4.6 前端

- `static/workflow_builder.js`：编辑 Agent 节点（`node_id`、`system_prompt`）、添加有向边、缩略图预览、`PUT` 保存。
- `static/app.js`：顶栏 `#workflow-select` 非 `default` 时在 body 中带 `workflow`（含 `__web__`）。
- 布局：`index.html` 两栏（`app-layout`），左侧工作流 + 右侧主内容；`styles.css` 中侧栏与 `wf-*` 样式。

### 4.7 保存时图校验（`_validate_workflow_dag_and_flow` + `_validate_workflow_dict`）

先 `YAMLWorkflowParser` 解析节点/边，再对**有向图**检查：

1. **唯一入口**：入度为 0 的节点恰好 1 个。  
2. **唯一最终输出**：出度为 0 的节点恰好 1 个（与 LangGraph 汇点、连到 `END` 的语义一致）。  
3. **无环**：Kahn 拓扑排序，处理不完则存在有向环。  
4. **无孤立**：从唯一入口正向 BFS 必须覆盖全部节点；从唯一出口沿反向边必须也能覆盖全部节点（保证每个节点都在「入口 → … → 出口」的主 DAG 上）。  
5. **无自环** `u→u`；**多节点**时若无边则无法同时满足唯一入/出度，会报错。  

校验失败返回 **HTTP 400**，`detail` 为中文说明。

## 五、PDF 上传到 `storage/pdfs/`

### 5.1 目录与版本控制

- 物理路径：仓库根 **`storage/pdfs/`**。  
- `.gitignore`：`storage/pdfs/*`，保留 `storage/pdfs/.gitkeep`，避免空目录不提交、又避免把用户 PDF 推上 Git。

### 5.2 模块 `ui/web/pdf_storage.py`

- `REPO_ROOT`：`ui/web/pdf_storage.py` 向上三级到仓库根。  
- `unique_pdf_path(original_name)`：文件名清洗、重名时加短随机后缀。  
- `list_pdf_files()`：按修改时间倒序列出 `*.pdf` 元数据。  
- `resolve_safe_pdf_path(filename)`：下载时仅允许 `storage/pdfs` 下真实 `.pdf` 文件，防 `..` 穿越。

### 5.3 限制

- 单文件上限 **50MB**（`MAX_PDF_BYTES`）。  
- 仅接受 **`.pdf`** 扩展名（上传接口侧检查）。

### 5.4 API

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/storage/pdfs` | `{ "files": [ { "name", "size", "modified" } ] }` |
| POST | `/api/storage/pdfs` | `multipart/form-data`，字段名 **`file`** |
| GET | `/api/storage/pdfs/{filename}/raw` | 下载（`FileResponse`） |

### 5.5 依赖

- `requirements.txt` 增加 **`python-multipart`**（FastAPI `UploadFile` / 表单需要）。

### 5.6 前端

- `static/pdf_storage.js`：页面加载时拉列表；上传成功后清空 input 并刷新；列表项为指向 `/raw` 的链接（新窗口打开/下载）。  
- `index.html`：「PDF 资料」区块；`styles.css`：`.pdf-panel` 等。

### 5.7 与 Agent 的衔接（当前未做）

- 上传仅**落盘 + 列表**；若要让工作流中某工具自动读某 PDF，需在工具或工作流里配置**绝对/相对路径**指向 `storage/pdfs/xxx.pdf`，可后续接 `file_loading_tool` 等。
